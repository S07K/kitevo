# Kitevo — CLAUDE.md (Agent Context)

## What is Kitevo

Kitevo is a creator-brand collaboration platform. Two sides:
- **Creators** build professional media kits (shareable pages with live Instagram/YouTube stats), apply to brand campaigns, and get discovered
- **Brands** post campaigns, browse/message creators via a discover page, and manage applicants

Stack: Next.js 16 App Router, Prisma + Supabase (Postgres), NextAuth, payments via `lib/payments` (Stripe or Dodo, per `PAYMENT_PROVIDER`), Tailwind v4, Resend (email), Vercel deployment.

## Key Technical Rules

- **Tailwind v4**: Use `@import "tailwindcss"` — `neutral` color unreliable, use `bg-muted`/CSS vars instead. Dark mode requires `@variant dark (&:where(.dark, .dark *));` in globals.css (class-based, not OS media query)
- **Prisma / migrations**: Schema changes ship as versioned migrations in `prisma/migrations`. Workflow: change `schema.prisma` → `npx prisma migrate dev --name <change>` against the LOCAL DB (env vars need both `DATABASE_URL` and `DIRECT_URL` inline: `DATABASE_URL=<local url> DIRECT_URL=<local url> npx prisma migrate dev …`) → commit schema + migration together. Locally, `npm run dev` applies pending migrations first (`predev` → `scripts/dev-migrate.cjs`, localhost databases only; skips with a warning otherwise). Deploys apply pending migrations automatically — GitHub Action `.github/workflows/db-migrate.yml` (tests first, then `migrate deploy`) and `scripts/vercel-build.cjs` before `next build` (**production builds only** — previews share the prod DB, so they skip it unless `MIGRATE_ON_PREVIEW=1`; a preview of a branch with a new migration runs on the old schema). NEVER use `prisma db push` on a migrations-managed (prod/staging) database: it drifts from history and accepts data loss. For NOT NULL columns on existing rows, author the migration SQL with a `DEFAULT` (or backfill-then-constrain). **Every migration must keep working with the previous deployment** (migrations apply before the new build goes live, and Vercel rollback reverts code only): additive changes ship in one release; drops/renames/type changes/`SET NOT NULL` ship as expand → contract over two releases, with a `pg_dump` first. Add a row to the migration table in DEPLOY.md §8a for each new migration. Rollback playbooks: DEPLOY.md §8a.
- **Avatar/logo uploads**: Stored as base64 data URLs in DB (resized client-side before upload). Max ~200k chars. Pattern: resize in browser → POST data URL → store in DB. **Instagram photo import** downloads the image server-side to base64 (`lib/image-to-data-url.ts`) — never stores the expiring `fbcdn` CDN URL. Render avatars via `AvatarImg` (falls back to initials on load error). Backfill: `scripts/backfill-instagram-avatars.ts`
- **Icons**: brand logos from `thesvg` (pinned exact; official full-colour marks) via `<BrandIcon brand="…" />` (`app/components/BrandIcon.tsx`); register each brand in `lib/brand-icons.ts` (subpath imports, `DARK_ON_DARK` for marks that vanish on navy, `GLYPH_IN_BRAND_COLOUR` where the default is a wordmark). `lib/brand-icons.test.ts` fails CI if an icon ever carries script/handlers (the SVG is injected as HTML). Generic icons from `lucide-react`. Never paste brand SVG paths by hand. Brands thesvg lacks (Stan Store, Beacons) use their official favicon in `public/brands/`. Payout-method marks live in `app/components/PayoutLogos.tsx`. When UI copy names a company inline (Razorpay, Stripe, PayPal, Google Drive, Dropbox, Notion…), use `BrandChip` (`app/components/BrandChip.tsx`; add the brand there, flag `darkOnDark` if its colour vanishes on navy).
- **Dark mode**: Managed via `next-themes`, class applied to `<html>`. The theme toggle lives in the account menus only: the sidebar account row (desktop workspace) and the NavAvatar popup (phones, non-workspace pages).
- **Brand colour / app theme**: ONE app theme (no palette switcher), from the owner-chosen palette: navy `#1B365D` (text/ink, primary hover), blue `#005A9C` (`--primary`), sky `#60C1E5` (`--accent`), aqua `#A0E0EF` (soft tints). Tokens in `globals.css`: `bg-primary text-primary-foreground` (+ `hover:bg-primary-hover`) for main actions, selected chips/toggles, progress and unread badges; `bg-primary-soft text-primary-soft-foreground` for niche tags, accent badges and the active sidebar item; `bg-accent text-accent-foreground` for "New"-style highlight pills; `--background` = white cards/inputs/menus, `bg-canvas` = cool light page and workspace backdrop (one step deeper so cards lift). Dark mode = navy surfaces with sky primary and dark text — so on `bg-primary`/`bg-accent` always use the matching `*-foreground`, never `text-white`/`text-background`. Never hardcode `bg-white`/greys/blues for surfaces or accents. The logo mark (`lib/logo.ts`) still uses its own indigo/terracotta/cream inks. Public kits ignore all of this — they use their kit style colours.
- **Kit styles**: free presets `warm/cool/paper/sage/mist/blush/lavender/noir` + Pro vibes, defined in `lib/kit-appearance.ts`. A new preset must be added to `KIT_THEME_CSS_VARS`, labels, `ALL_VALID_PRESETS`, `kitChartColors` (cover, charts, donut), `lib/pdf-theme.ts`, the PPTX `THEME` map and `VIBE_COLORS` in `KitActions.tsx`.
- **Comped access** (`User.compedTier`): grants a tier's entitlements (kits, verified badge, inquiry inbox) with NO subscription, for beta/press/grandfathering. A tier id or null, set with `scripts/comp-user.ts <email> <pro|brand|none>` per-user, or auto-applied to **every new signup** while `BETA_AUTO_COMP_TIER` names a tier (`lib/beta-comp.ts`, spread into both the email and Google signup creates; unset at launch, vercel-build warns if left on in production). Never a fake subscription (no customer id, survives provider swaps). `config/resolveVerifiedTier(subscriptionTier, compedTier)` is the one rule — subscription wins, comp is the floor — used at every verifiedTier write site (webhook, subscription-status) so a comp is never cleared by subscription syncing. `getAllowedKitsForUser` takes the max of comp and subscription. During beta, `BETA_AUTO_COMP_TIER=pro` auto-comps every new signup (both email and Google paths, via `lib/beta-comp.ts`); unset it at launch.  **Beta testers should be comped, never sent through test checkout** — test-mode checkout writes a real verifiedTier + a dead test customer id that has to be reconciled at go-live.
- **Platform tokens are encrypted at rest** (`lib/token-crypto.ts`, AES-256-GCM, key ring in `TOKEN_ENCRYPTION_KEYS`, first key active). Every write of `instagramAccessToken`/`youtubeAccessToken`/`youtubeRefreshToken` goes through `encryptToken`; every read that sends a token to Meta/Google wraps the row in `decryptPlatformTokens(...)`. Truthiness checks ("is connected") don't need decrypting. Undecryptable → null → treated as disconnected (fail closed). Legacy plaintext passes through until `scripts/encrypt-platform-tokens.ts` runs. Google sign-in tokens are not stored at all.
- **Funnel analytics** (`lib/analytics.ts`, `AnalyticsEvent` table): `trackEvent(name, { userId, props, dedupeKey })` with a closed name set (`ANALYTICS_EVENTS`) — add a name there before using it. Never throws; props carry no PII/tokens. "First time" events pass a `dedupeKey` (unique; inserted with `skipDuplicates`). Wired: signup (email + Google), onboarding_complete, kit_created, kit_first_view (non-owner, public kit page), checkout_started, upgrade + subscription_canceled (webhook). Report: `npx tsx scripts/funnel-report.ts [days]`. GA4 stays for page traffic only.
- **Referral program** (`lib/referrals.ts`, see PLAN.md §13): terms live in `REFERRAL_TERMS` in `lib/referral-terms.ts` (client-safe; marketing copy, estimator and ledger all read it — never hardcode "20%"). Attribution = `kitevo_ref` cookie (set client-side by `ReferralCapture` in the root layout, first touch wins) read at both signup paths. Commissions come ONLY from the `payment.succeeded` domain event and are idempotent on `paymentId`; refunds go through `applyRefundToCommission` (reverse unpaid, negative clawback row if already paid). Money = integer minor units of the settlement currency. "Available" is derived (`pending` && `availableAt <= now`), never stored. Payouts are manual: `/admin/payouts` (gated by `ADMIN_EMAILS` via `lib/admin.ts`, 404 for others; no CSV, everything on-page) → pay → `recordPayout` marks exactly the commissions it summed, in a transaction. Payout destination + tax ID are encrypted with `lib/token-crypto`.
- **Admin ops** (`/admin`, gated by `ADMIN_EMAILS`, 404 otherwise): every payment webhook is logged to `WebhookEvent` as its *domain event* (never the raw provider body) by `lib/webhook-log.ts`; what an event does lives in `lib/payment-events.ts` (`applyPaymentEvent`), shared by the route and admin Replay. Providers expose `webhookDeliveryId` so retries of an applied delivery are acknowledged, not re-applied. Comp/plan changes go through `lib/admin-actions.ts` (`setComp`, `resyncPlan`: live provider subscription → `resolveVerifiedTier`, keeps hand-granted `top_creator`, writes nothing if the provider lookup fails) and are written to `AdminAuditLog`. Prefer Resync over Replay for plan state — replaying an old `subscription.changed` can regress it.
- **Transactional email** (`lib/email.ts`, Resend): every user-supplied string goes through `escapeHtml` / `quote()` before it lands in HTML (visitors and creators control names, pitches, messages). Emails triggered by a user action are sent with `inBackground(label, task)` (`lib/background.ts`, Next `after()`), so a slow or failing send never blocks or fails the action. Campaign emails: brand on a new application; creator when a brand accepts/declines — only on an actual status change, never on re-clicks or a move back to pending.
- **Usernames** = public URLs, so rules live in `lib/username.ts` (`usernameProblem`, `RESERVED_USERNAMES`). Add any new top-level route to the reserved list. Profile PUT only validates a *changed* username. Niches list: `lib/niches.ts`.
- **`/api/subscription-status` reads the provider through `lib/subscription-cache.ts`** (60s `unstable_cache`, tag per customer) because dashboard/settings/pricing hit it on every load. Any code that changes a plan must call `invalidateSubscription(customerId)` — `applyPaymentEvent`, the in-app upgrade and admin resync already do. Webhooks/upgrades/admin read the provider directly, never via the cache. The dashboard renders once the profile loads; plan-dependent sections (metrics, plan panel, kit limits) wait for the status on their own.
- **Trials & coupons** (`lib/trials.ts`): Pro-only free trial, `PRO_TRIAL_DAYS` (default 14, 0 = off). `getTrialEligibility` is the one rule (creator, verified email, never had a provider customer id, not comped Pro) and the checkout route enforces it; `GET /api/me/trial` only labels buttons. The client asks with `trial: true` and never sends a length. Dodo checkout always sends `subscription_data.trial_period_days` (0 when not trialing) so a product-level trial can't leak. Discount codes: created in the provider dashboard; checkout takes a sanitised `code` (`cleanDiscountCode`), and a rejected code falls back to a plain checkout where the customer can type one. Trials grant access with no `payment.succeeded`, so no referral commission until the first real charge.
- **Custom domains** (`lib/custom-domains.ts`, `lib/custom-domain-host.ts`): one `CustomDomain` per kit, Starter/Pro (`canUseCustomDomain`: comp or active sub, via the subscription cache). Domains are added to the Vercel project with the Vercel REST API (`VERCEL_API_TOKEN`, `VERCEL_PROJECT_ID`, optional `VERCEL_TEAM_ID`); Vercel issues TLS, DNS pointing is the ownership proof, and Vercel's own TXT challenge is passed through when it asks. **`middleware.ts` now matches every path**: a non-Kitevo Host (`isAppHost` — app URL + www, localhost, `*.vercel.app`, `APP_HOSTS`) rewrites `/` to `/custom-domain/[host]`, passes `/api`, `/_next` and files, and 308s everything else to Kitevo; `/custom-domain/*` 404s on Kitevo's own hosts; the old signed-in matcher is the `PROTECTED` list there (add new signed-in routes to it). The domain page renders the real kit page, with canonical = the custom domain; a lapsed plan redirects to `/kit/<slug>`; first HTTPS visit marks it active. Kit and account deletion call `releaseDomains` first (the row cascades, the Vercel domain wouldn't). Unverified claims > 7 days can be taken over; live ones never.
- **Free tools** (`/tools`, `/tools/rate-calculator`, `/tools/engagement-rate-calculator`; SEO top of funnel, no login): all maths in `lib/creator-calculators.ts` (client-safe, tested). Every constant is a rule of thumb or our weighting, and the page's "How the estimate works" prints them from that file — **never present results as market data or "what creators like you earn"**, never cite a study. Pages use `app/tools/ToolPage.tsx` (breadcrumb, method, FAQ, WebApplication + FAQPage JSON-LD, live-kit CTA) and the blog chrome. Hand-offs: engagement → rate calculator via query params (`platform`, `er`, `followers`, `views`); the rate calculator's CTA saves mid-point rates to localStorage (`CALCULATOR_RATES_KEY`, 30-day TTL) and `app/kit/edit/CalculatorRatesOffer.tsx` offers them once in the editor's Rates section while the kit has no priced rates. In the sitemap; "tools" is a reserved username.
- **Book a call (kit button, integrations-first)**: creators connect their own **Calendly, Cal.com or Google Calendar appointment schedule** in Connectors → Scheduling (`SchedulerConnection`, one per provider, public link; `/api/scheduling/connections`). Each kit has `Kit.booking` JSON `{ url, label }` (`lib/kit-booking.ts`: `normalizeKitBooking`, `publicBooking`), set in the kit editor's **Contact card** (`app/kit/edit/BookCallField.tsx`) and saved by the kit PUT (Google short links resolved via `parseSchedulerInput`; unknown links → 400). The kit shows a **Book a call** button **under the profile bio** (in the sticky identity rail on wide screens, right under the profile on phones; its own `data-kit-section="contact"` so a preview tap opens the Contact card) that opens `BookCallDialog` — the scheduler iframe, **portalled to `<body>`** because the kit's `@container` re-anchors fixed elements; `?book=1` opens it on load. It renders only while that scheduler is still connected (`publicBooking(booking, view.schedulers)`; `loadKitViewData` returns `schedulers`). Embed URLs are rebuilt by `parseSchedulerUrl` (known hosts only; Calendly `?embed_type=Inline`, Cal.com plain page URL, Google `…/appointments/schedules/<id>?gv=true`). **Booking products are retired** (they sat in the Shop but acted like a button): `normalizeProductInput` always saves `type: "download"`, Products/the Shop list downloads only, and `/p/<old booking id>` 307s to `/kit/<slug>?book=1`. Migration `20261104161344_kit_book_a_call` copied each creator's first published booking product onto their kits; the old rows stay (unused). The scheduler owns availability, calendar conflicts, reminders and payment.
- **Brand deals** (`lib/deals-shared.ts` client-safe rules, `lib/deals.ts` state machine, `lib/deal-payments.ts`, `lib/deal-access.ts`): a `Deal` between a creator and a brand (account `brandUserId`, or email-only for kit inquiries) with numbered `DealVersion`s (deliverables, amount in minor units, currency, `paymentPlan` upfront | split (`advancePct`) | on_delivery, due date, notes), `DealPayment`s and an append-only `DealEvent` timeline both sides see. **Transparency rules** (`allowedActions`): only the side a version awaits can accept/decline; the proposer can withdraw; agreed terms can be revised by either side only until money moves (then fixed); cancelling is impossible once anything is paid; only the creator marks delivered. Every action runs in a transaction that re-checks the rule and writes an event. Accepting rebuilds unpaid payments from `splitPlan` (acceptance parts `due`, delivery parts `scheduled` until delivered); delivered + all paid → completed. **Money is creator-owned**: payments go straight into the creator's own Razorpay/Stripe/PayPal through the same verified flows as products (DealPayment id as the provider "order" id; `/api/deal-payments/[id]/pay|confirm|stripe-return|paypal-return`; `reconcile` asks the provider before restarting a pending payment); `markDealPaymentPaid` is conditional so only the first confirmation counts. Kitevo takes 0%, every plan. Access: creator/brand by session, or the brand's private `/d/<brandToken>` link (no account; strangers get 404). The other party is always derived server-side from the source (application, conversation, inquiry, or a creator's direct deal). Entry points: accepted application (creator "Send your quote", brand "Send offer"), message thread header, Pipeline inquiry, `/deals/new`. Emails to the other side at each step via `sendDealEmail`. "deals" and "d" are reserved usernames; `/deals` is in middleware `PROTECTED`.
- **Copilot** (`lib/copilot.ts`, `lib/copilot-prompts.ts`, `lib/copilot-stats.ts`, `lib/ai/`): AI drafts for a creator's bio (kit editor Profile), campaign pitch (Apply), inquiry reply (Pipeline → "Open in email") and **message drafts** in brand threads (task `message`: a reply when the brand spoke last, a follow-up when the creator did; last 12 messages, brand messages as `<brand_text>`, refused across a block; the creator composer is a growing textarea, Enter sends, Shift+Enter new line), via `POST /api/copilot { task }` + `<CopilotDraft>`. **Provider-agnostic, no SDK**: `lib/ai/client.ts` speaks OpenAI Chat Completions (Groq, OpenRouter, OpenAI, Gemini, `custom` base URL) and Anthropic Messages. Default model for Groq and OpenRouter is `openai/gpt-oss-120b` (a reasoning model: `complete` adds `reasoning_effort: "low"` and token headroom for gpt-oss only, or drafts come back empty). Whose key: the creator's own `AiConnection` (Connectors → "AI for Copilot", one per user, key via `encryptToken`, checked with `verifyAiKey` before saving, only `keyHint` ever returned) → any plan, no cap; else Kitevo's env key (`AI_PROVIDER`/`AI_API_KEY`/`AI_MODEL`/`AI_BASE_URL`) → **Pro only**, `COPILOT_MONTHLY_LIMIT` (default 50) per UTC month counted in `CopilotUsage` (failed generations don't count); no key at all → nothing is sent. **Grounding rules**: the server builds every prompt from DB facts (`creatorFacts`: profile, kit rates/brands, stats via `statFacts` labelled live vs self-reported) — the client only names the task; brand-written text is wrapped in `<brand_text>` as data; the model is told never to invent numbers, collaborations or terms; output goes through `cleanOutput` and is always shown for review before use. **Never let Copilot write deal terms** (deal notes were deliberately excluded). Rate suggestions (`GET /api/copilot/rates`, `SuggestRates`) are the rate calculator's formulas on the kit's own numbers — no AI, every plan, not counted. Analytics: `copilot_used { task, source }`. `/admin` shows Copilot usage (30-day drafts by task and key, active creators, own-key providers, heaviest users vs the cap) and an Open reports stat.
- **Report & block** (`lib/safety.ts` server, `lib/safety-shared.ts` client-safe; `UserBlock`, `InquiryBlock`, `UserReport`, `User.suspendedAt`). A block either way stops **new** contact: conversations + messages (`blockedGuard` in both conversation routes; the list returns `blocked: "me" | "them" | null` and the inbox swaps the composer for `BlockedNotice`), campaign applications, new deals and new deal terms (propose/accept). It never traps anyone in a deal: decline, withdraw, cancel, deliver and payments still work, and existing threads/deals stay readable. Blocked accounts drop out of each other's Discover and campaign feeds (`blockedIdsFor`). Kit-inquiry senders (no account) are blocked by email: their inquiries return 201 and are silently dropped. `<SafetyMenu userId name context />` ("⋯ → Block / Report") sits in message threads, deal pages, campaign detail (creator side) and applicant rows; Settings has a Blocked panel to unblock. Reports (`POST /api/safety/report`, reason from `REPORT_REASONS`, optional note ≤1000, optional `alsoBlock`) email `ADMIN_EMAILS` (`sendReportAlert`, no note in the email) and land in **`/admin/reports`** (Dismiss / Suspend account). The reported account is never told who reported. **Suspension** (`suspendUser`/`unsuspendUser` in `lib/admin-actions.ts`, audited, closes all their open reports): sign-in refused (credentials throw `ACCOUNT_SUSPENDED`, Google returns to `/login?error=ACCOUNT_SUSPENDED`), workspace + kit-editor layouts render `SuspendedScreen` (JWT sessions outlive sign-in checks), `activeGuard` refuses guarded actions, and their public kit, profile, campaigns and inquiry form 404 (`suspendedAt: null` filters). **Any new route where one account can reach another (message, apply, offer, invite) must call `activeGuard` + `blockedGuard`.**
- **Connectors tab** (`/connectors`, creators; sidebar under Home, phone avatar menu): every account a creator connects in one place — Instagram + YouTube (OAuth `return_to=connectors`), Razorpay (`ConnectRazorpayDialog`), Stripe (`ConnectStripeDialog`) and PayPal (`ConnectPayPalDialog`), each once per account; every paid product uses them. Products only asks for a price; its rail just shows payment status and links here. Dashboard/Settings Connections panels link to it. Result banners read `lib/connect-messages.ts`. Add a new provider here, not on Products. "connectors" is reserved and in middleware `PROTECTED`.

Other public pages use `BlogHeader`/`BlogFooter` with `width` = the page's main container (`3xl` blog/privacy/terms/help, `4xl` compare index + signed-out pricing, `5xl` tools/integrations/referral, `6xl` compare detail) so the logo, content and footer share one left edge. New public page: pass its width.
- **Modals** (`workspace/Modal`): capped at the viewport; the body scrolls and a `footer` prop pins actions (use it for long forms). Sizes sm/md/lg.
- **Integrations page** (`/integrations` + landing `IntegrationsStrip`, both from `lib/integrations.ts`): Instagram, YouTube, Razorpay, Stripe, PayPal (all live), Drive/Dropbox/Notion delivery, custom domain. Logos via `app/components/IntegrationLogo.tsx` (BrandIcon). Only mark `live` what has shipped, keep plan labels in step with `config/subscriptions.ts`, and data-use lines with what the code reads ("only reads, never posts"). Flip a new integration to `live` only when it ships. In the sitemap and footer; "integrations" is a reserved username.
- **Comparison pages** (`/compare`, `/compare/[slug]`, data in `lib/comparisons.ts`): every competitor claim carries a `Source` (`official` = their own site/help centre, `reported` = an independent review, labelled as such on the page); unsourced competitor cells are `UNCONFIRMED` ("—", explained under the table). Never claim a competitor lacks something unless their own docs say so, and state Kitevo's gaps (`KITEVO.commerce` says no digital products yet; update it when commerce ships). Kitevo prices come from `config/subscriptions.ts`. Bump `CHECKED_ON` whenever facts are re-checked. Linktree's prices are `reported` (linktr.ee was unreachable from the dev network); upgrade them to official when verified. In the sitemap; "compare" is a reserved username.
- **Marketing art (blog + compare)**: built from the landing cutouts (`KitCard`, `Cutout`), never stock photos or copies of another product's UI. Blog posts pick a cover with `cover: kit | pitch | examples` in frontmatter (`app/blog/BlogArt.tsx`, shown on the index and atop the post). Compare pages use `app/compare/CompareArt.tsx`: competitor logos from `thesvg` where available (Linktree, Canva), else the company's **official favicon downloaded from its own site** into `public/brands/` (Stan, Beacons) — never hand-drawn. - **Creator commerce** (`lib/commerce.ts` server + `lib/commerce-shared.ts` client-safe; PLAN.md payout-rail decision). Money model: **creator-owned payments** — buyers pay the creator's own Razorpay, Stripe or PayPal account; Kitevo never holds funds or pays out. Release A (live code): `Product` (per creator, draft/published, cover as base64, `deliveryUrl` = creator's file link, web URLs only) + `Order` (every claim is an order; free claims `status: "free"`, paid will reuse it; `accessToken` opens the buyer's private `/o/[token]` page — the **only** place the delivery link renders). Public: `/p/[id]` product page in the creator's kit style (drafts owner-only), `POST /api/products/[id]/claim` (no account, rate-limited per IP + email, same email → same order, emails the link via `sendDownloadEmail` in the background). Kit "Shop" section (`data-kit-section="products"`, `sectionVisibility.products`), editor Shop card → `/products` workspace page (create/edit/publish, downloads list with copy-all-emails). Never import `lib/commerce.ts` from client code (it loads Prisma); use `commerce-shared`. "p", "o", "products" are reserved usernames; buyer data is covered in the privacy policy ("Download sign-ups"). **Release B (paid, Razorpay):** creators paste their own Key ID + Secret (`PaymentConnection`, one per provider, secret via `encryptToken`, verified against Razorpay before saving; `lib/payment-connections.ts`, never return the secret — `publicConnection`). `lib/razorpay.ts` = tiny REST client (no SDK) + `verifyPaymentSignature` (HMAC order|payment, constant-time). Price is stored in minor units (`priceCents`, `currency` INR/USD, min 1.00; `formatPrice`). Paid products need **Starter/Pro** (`lib/creator-plan.ts` `hasPaidCreatorPlan`, shared with custom domains) **and** a connection: enforced on publish (`paidPublishProblem`), at checkout, and on display (`canSellPaid` — unsellable paid products are hidden from the kit and their page says "not on sale"). Flow: `POST /api/products/[id]/checkout` (amount from the product, never the client) → pending `Order` + Razorpay order on the creator's account → Razorpay Checkout (script from checkout.razorpay.com) → `POST /api/orders/[id]/confirm` verifies signature, fetches the payment (order/amount/currency must match, captures if only authorized) → `markOrderPaid` (`lib/paid-orders.ts`: conditional update so only the first confirmation emails). No webhooks (creators would have to configure them): a buyer who paid but lost the confirmation gets their link back when they start checkout again (`recoverPaidOrder` checks the earlier Razorpay orders). Pending orders never count as sales or appear in buyer lists. Paid orders earn no referral commission (creator revenue, not Kitevo's). **Stripe (creator-owned):** a **restricted key** (`rk_…`, only "Checkout Sessions: Write"; full `sk_` keys are refused) stored like the Razorpay secret (`publicKey` holds only its hint). `lib/stripe-creator.ts` = fetch-based client (the `stripe` SDK stays exclusive to `stripe-provider.ts`, which is Kitevo's own billing). Checkout creates a Stripe-hosted Checkout Session (`provider: "stripe"` in the checkout body) and redirects; Stripe returns the buyer to `GET /api/orders/[id]/stripe-return?session_id=…`, which retrieves the session from the creator's account and requires `sessionPaysFor` (paid + this order's metadata + amount + currency) before `markOrderPaid`, else back to `/p/[id]?checkout=<reason>`. Recovery covers both providers. With several connected the buy box offers a choice; `canSellPaid`/`paidPublishProblem` accept any. **PayPal (creator-owned):** the creator's own REST app Client ID + Secret (`savePayPalConnection`; Client ID stored plain, Secret encrypted; live vs sandbox detected by `detectPayPalEnv` and kept in `livemode`). `lib/paypal-creator.ts` (fetch, Orders v2): create with `custom_id` = our order id and a `PayPal-Request-Id`, redirect to the payer-action link; PayPal returns to `GET /api/orders/[id]/paypal-return?token=<pp order>`, which captures (idempotent: `ORDER_ALREADY_CAPTURED` → fetch) and requires `paypalPaysFor` (COMPLETED, this order, amount, currency) before `markOrderPaid`. Recovery captures APPROVED-but-uncaptured orders. **PayPal can't take INR** (PayPal India stopped domestic payments): `paypalSupports` limits it to `PAYPAL_CURRENCIES` (USD); checkout and the buy box skip it for INR, `canTake`/`canSellPaid(userId, currency)` hide paid products no connected account can take, and `paidPublishProblem` refuses INR when PayPal is the only account (`currency_unsupported`).
- **Payments go through `lib/payments`, never a provider SDK directly.** Two implementations: `stripe-provider.ts` and `dodo-provider.ts`, selected by `PAYMENT_PROVIDER` (default stripe; an unknown value throws rather than falling back). `config/subscriptions.ts` reads the same var to pick `STRIPE_PRICE_ID_*` vs `DODO_PRODUCT_ID_*`. **Dodo differences that bit us:** it spells cancellation `cancelled` (Stripe: `canceled`), has no `trialing`, uses `on_hold` for past-due, calls a price a `product`, and its checkout-session retrieve returns payment status only — no customer or subscription id — so Dodo cannot exchange a session for a customer and `isCheckoutSessionId` returns false. Instead Dodo appends `subscription_id`/`payment_id`/`status` to the return URL; the success pages (dashboard, brand settings, onboarding) send `subscription_id` to `/api/subscription-status`, which looks it up via `payments.getSubscriptionById` and links it **only if its `kitevo_user_id` metadata is the signed-in user** (webhooks never reach localhost, and can lag in prod). The webhook (`subscription.active` carries customer + metadata + product) stays the source of truth. The success URL only includes Stripe's `{CHECKOUT_SESSION_ID}` placeholder when `payments.checkoutSessionPlaceholder` is true. **Vitest gotcha:** `beforeEach(() => mock.mockReset())` returns the mock, and vitest runs a returned function as teardown — use braces. Dodo webhooks use the Standard Webhooks spec (`webhook-id`/`webhook-signature`/`webhook-timestamp`), not a Stripe-style single header. `PaymentProvider` (`lib/payments/types.ts`) is the contract; `stripe-provider.ts` is the only file that may import `stripe` or know what a `cs_` prefix means. Adding a provider (Dodo, Paddle) = one new file implementing the interface + selecting it in `lib/payments/index.ts`. Webhooks are translated into domain events (`checkout.completed`, `subscription.changed`, `subscription.canceled`, `ignored`) so the webhook route has no provider vocabulary. Unknown subscription statuses normalise to `inactive`, i.e. fail closed — never grant access on a status we don't recognise. ## Prisma Schema Notes

- `User.niches` — `String?` JSON string[] of creator content niches
- `User.verifiedTier` — `String?` values: `creator_pro`, `top_creator`, `brand_verified`, null
- `User.accountType` — `"creator"` | `"brand"`
- `BrandProfile.companyName/logoUrl/industry/budgetRange/website/description`
- `Campaign.status` — `"open"` | `"closed"` | `"draft"`
- `CampaignApplication.status` — `"pending"` | `"accepted"` | `"rejected"`
- `CampaignApplication.updatedAt` — added but may need `prisma generate` confirmation
- `SavedCreator` — brand↔creator shortlist join (`@@unique([brandId, creatorId])`, named relations `BrandSaved`/`SavedByBrand`)
- `CampaignView` — campaign view events (`campaignId`, nullable `viewerId`, `referrer`); owner views not recorded
- `User.followerCount/engagementRate/statsUpdatedAt` — cached creator stats for discover filtering (refreshed from IG/YT via `lib/creator-stats-cache.ts`)
- **Schema changes are versioned migrations** (`prisma/migrations`, baseline `20261031000000_init`), applied automatically on deploy: GitHub Action `.github/workflows/db-migrate.yml` (after `npm test`) and `scripts/vercel-build.cjs` before `next build`, both via `prisma migrate deploy`. Author new migrations locally with `prisma migrate dev`; never reach for `db push` against prod/staging
- **Supabase needs two connection strings**: `DATABASE_URL` = transaction pooler (:6543, `?pgbouncer=true`) for runtime, `DIRECT_URL` = session pooler (:5432) for `prisma migrate deploy` (and the same two values must exist as GitHub repo secrets for the Action). Never Supabase's "direct connection" — it is IPv6-only without the paid add-on. See DEPLOY.md step 2
- **New/foreign databases still need baselining before `migrate deploy`**: db built via the old `db push` flow (e.g. a staging DB cloned this way) has no `_prisma_migrations` history and fails closed with `P3005` until `db push` + `migrate resolve --applied <migration>` sync it. Prod was baselined 2026-10-31 (first Action run: "No pending migrations"). See DEPLOY.md step 2
